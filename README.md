# Real-Time Smart-Meter Streaming Analytics

This mini-project replays household electricity readings as a live Kafka stream, computes windowed metrics, scores unusual power values with Isolation Forest, stores both history and current state in MySQL, and displays the result in an auto-refreshing Streamlit dashboard.

It follows the six-layer architecture from `MiniProject_Guide.pdf`:

1. Data source: `data/household_power.csv`
2. Streaming tool: Apache Kafka and the `smartmeter-events` topic
3. Stream processor: Python and `deque(maxlen=30)`
4. ML algorithm: offline-trained `IsolationForest`
5. Database serving layer: MySQL history plus one current-state row
6. Visualization: Streamlit with timed refresh

## Architecture

```mermaid
flowchart LR
    A[Smart Meter CSV] --> B[Kafka Producer]
    B --> C[Kafka Topic]
    C --> D[Python Stream Processor]
    D --> E[Sliding Window Metrics]
    E --> F[Isolation Forest]
    F --> G[MySQL]
    G --> H[Streamlit Dashboard]
```

The CSV producer sends one JSON event at a time. The processor keeps the latest 30 power values in memory, calculates the current value, rolling average, running peak, approximate energy, and anomaly flag, then writes one history row and updates the singleton metrics row. The dashboard reads only recent history and the current-state row, so it does not scan the whole table on every refresh.

## Kafka decision: KRaft, not ZooKeeper

Use a recent Apache Kafka 4.x binary distribution in single-node KRaft mode. This project intentionally does not use ZooKeeper commands. Current Kafka quickstarts use Java 17+ and format a standalone KRaft server with `kafka-storage`; see the [Apache Kafka quickstart](https://kafka.apache.org/quickstart/).

If you choose an older Kafka 3.x distribution, follow that distribution's KRaft configuration path consistently. Do not combine a 3.x `config\kraft\server.properties` setup with ZooKeeper startup commands or with a 4.x setup.

## Prerequisites

- Windows 10/11 and VS Code
- Python 3.11 or newer
- Java 17 or newer for modern Kafka
- Apache Kafka 4.x extracted, for example to `C:\tools\kafka_2.13-4.3.1`
- MySQL 8.x server and the `mysql` command-line client

```powershell
py -3.11 -m venv .venv
```

## Environment configuration

Copy `.env.example` to `.env`. The defaults expect Kafka at `127.0.0.1:9092` and MySQL at port `3306`.

Important values are:

- `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`
- `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_TOPIC`, `KAFKA_GROUP_ID`
- `STREAM_DELAY`, the producer pause in seconds between events
- `DASHBOARD_REFRESH_SECONDS`, the browser refresh interval
- `ENERGY_INTERVAL_MINUTES`, normally `1.0` for the per-minute example data

The application never hardcodes a database password in Python source. `config.py` loads `.env` and centralizes all paths and endpoints.

## Kafka setup on Windows

Open a PowerShell terminal and set the Kafka directory:

```powershell
$env:KAFKA_HOME = "C:\tools\kafka_2.13-4.3.1"
Set-Location $env:KAFKA_HOME
```

Format a new single-node KRaft log directory once:

```powershell
$clusterId = (& ".\bin\windows\kafka-storage.bat" random-uuid).Trim()
& ".\bin\windows\kafka-storage.bat" format --standalone -t $clusterId -c ".\config\server.properties"
```

Start Kafka and leave this terminal open:

```powershell
& ".\bin\windows\kafka-server-start.bat" ".\config\server.properties"
```

In another terminal, create the project topic once:

```powershell
$env:KAFKA_HOME = "C:\tools\kafka_2.13-4.3.1"
& "$env:KAFKA_HOME\bin\windows\kafka-topics.bat" --create --if-not-exists `
  --topic smartmeter-events --bootstrap-server 127.0.0.1:9092 `
  --partitions 1 --replication-factor 1
```

Verify it:

```powershell
& "$env:KAFKA_HOME\bin\windows\kafka-topics.bat" --describe `
  --topic smartmeter-events --bootstrap-server 127.0.0.1:9092
```

## MySQL setup

Start MySQL, then run the schema as an administrator. From the project root:

```powershell
Get-Content .\sql\setup.sql | mysql -u root -p
```

The script creates the `smartmeter` database, the `meter_app` account used by `.env.example`, the history table `meter_readings`, and the singleton current-state table `meter_metrics`.

The processor and dashboard use parameterized SQL statements, including the validated integer row limit used by the read-only dashboard query.

## Milestone 1: CSV → Kafka → terminal output

Files: `src/producer.py`, `src/consumer.py`, `src/config.py`, `.env`.

Terminal A, from the project root with the virtual environment active:

```powershell
python src/consumer.py
```

Terminal B:

```powershell
python src/producer.py --max-rows 5 --delay 0.2
```

Expected output is five dictionaries like:

```text
{'reading_time': '2006-12-16 17:24:00', 'global_active_power': 4.216}
```

Verification: the producer logs `Producer stopped after sending 5 events`, and the terminal consumer prints five JSON-derived events. Invalid numbers, empty strings, `?`, negative values, and invalid timestamps are skipped instead of terminating the producer.

Likely errors:

- `NoBrokersAvailable`: Kafka is not running, the topic endpoint is wrong, or the Windows firewall is blocking port 9092.
- `CSV dataset not found`: run the command from the project root or set `CSV_PATH` in `.env`.
- No terminal output: start the consumer before the producer and check the topic name.

## Milestone 2: Kafka → processor → MySQL

Files: `src/processor.py`, `src/database.py`, `sql/setup.sql`.

This milestone exercises the sliding window and database serving layer without ML:

```powershell
python src/processor.py --disable-ml
```

In another terminal:

```powershell
python src/producer.py --max-rows 30 --delay 0.2
```

The `--disable-ml` flag is only for this milestone. It leaves anomaly flags at zero while proving that events can be consumed, inserted, and reflected in `meter_metrics`.

Verification query:

```powershell
mysql -u meter_app -p -D smartmeter -e "SELECT COUNT(*) AS readings FROM meter_readings; SELECT * FROM meter_metrics;"
```

Expected result: the row count increases, `current_power` equals the latest event, `rolling_avg` uses no more than 30 values, and `peak_power` is the largest value seen by that processor run.

## Milestone 3: Kafka → Isolation Forest → MySQL

Train once before starting the ML-enabled processor:

```powershell
python src/train_model.py
```

Expected log:

```text
Saved model to ...\models\anomaly_model.pkl using ... clean readings
```

Then start the normal processor:

```powershell
python src/processor.py
```

The model is loaded once at startup. Each live power value is passed as a one-column DataFrame with the same feature name used during training, avoiding feature-shape/name warnings. Isolation Forest returns `1` for normal and `-1` for anomaly; the database stores the dashboard-friendly flag `0` or `1`.

Verification query:

```powershell
mysql -u meter_app -p -D smartmeter -e "SELECT reading_time, global_active_power, rolling_avg_30, is_anomaly FROM meter_readings ORDER BY reading_pk DESC LIMIT 10;"
```

The included sample contains high spikes near `14.800` and `17.500` kW to make anomaly behavior visible. Exact flags depend on the fitted model and the number of rows consumed.

## Milestone 4: complete dashboard

Start the dashboard from a separate terminal:

```powershell
streamlit run src/dashboard.py
```

Open the displayed local URL, normally `http://localhost:8501`, then start or restart the producer:

```powershell
python src/producer.py --delay 0.2
```

The dashboard shows current power, 30-reading rolling average, peak power, total energy, anomaly count, a live power/average chart, red anomaly points, and a recent anomaly table. The SQL query retrieves recent rows in descending order for efficiency; `database.py` sorts them ascending before plotting so the graph is chronological.

## Exact startup order for the full demo

Use one terminal per long-running process:

1. Start MySQL.
2. Start the single-node Kafka KRaft server.
3. Create `smartmeter-events` if it does not already exist.
4. Apply `sql/setup.sql` if this is a new database.
5. Activate the Python virtual environment.
6. Train the model with `python src/train_model.py`.
7. Start `python src/processor.py`.
8. Start `streamlit run src/dashboard.py` and open the browser.
9. Start `python src/producer.py --delay 0.2` last.

Starting the producer last makes the live movement visible. Press Ctrl+C in the producer to demonstrate that the dashboard refreshes but stops changing when no new data arrives.

## Common errors and fixes

| Symptom | Fix |
| --- | --- |
| `NoBrokersAvailable` | Start Kafka, verify `KAFKA_BOOTSTRAP_SERVERS`, and check port 9092. |
| Model file missing | Run `python src/train_model.py` before the normal processor. |
| MySQL access denied | Re-run `sql/setup.sql` as root and align the `.env` credentials. |
| Unknown database/table | Apply `sql/setup.sql` and confirm `MYSQL_DATABASE=smartmeter`. |
| Dashboard is empty | Start processor first, then producer; inspect the processor terminal. |
| Dashboard looks frozen | The refresh timer only re-queries; confirm the producer is still sending. |
| Invalid numeric value | The producer and trainer coerce bad values and skip unusable rows. |
| Duplicate data after restart | Use a new `KAFKA_GROUP_ID` for a clean replay, or clear the topic/database intentionally for a fresh demo. |
| Windows script cannot run | Use the `.bat` files under `bin\windows` and run PowerShell from the Kafka directory. |

## Report and viva explanation

### Abstract

This project turns historical smart-meter CSV data into a paced event stream. Kafka decouples ingestion from processing, Python computes a 30-reading sliding average and running metrics, Isolation Forest flags unusual consumption without labelled anomaly data, MySQL serves history and current state, and Streamlit displays a self-refreshing live view.

### Why each layer exists

- The CSV is a reproducible sensor source.
- Kafka provides a durable event channel and separates the sender from the processor.
- The processor maintains state between events and performs windowed analytics.
- Isolation Forest learns normal behavior offline and scores events quickly online.
- MySQL decouples the continuously running processor from dashboard reads.
- Streamlit makes the changing state visible and refreshes on its own.

### Key viva answers

- **Why `deque(maxlen=30)`?** It automatically removes the oldest value when the 31st arrives, so the average always uses the latest 30 readings with bounded memory.
- **Why train/serve split?** Training is a slower offline operation. The live processor loads the artifact once and only predicts, so event latency stays small and behavior is reproducible.
- **What does contamination mean?** `0.01` tells Isolation Forest that roughly 1% of training values may be abnormal; it is a tuning assumption, not a guaranteed truth.
- **Why two database tables?** `meter_readings` preserves history for charts, while `meter_metrics` is a tiny latest-state row for fast KPI reads.
- **Why is the dashboard truly live?** Fresh rows are written continuously and the browser triggers a fresh database query every few seconds. Either part alone is insufficient.
- **How is energy estimated?** With power in kW and one reading per minute, each event contributes approximately `power × 1/60` kWh.

## Future improvements

- Use a production Kafka cluster with replication and schema validation.

- Add hourly energy windows and alert notifications.
- Compare contamination values and evaluate precision/recall on labelled events.
- Add authentication, dashboard filters, and retention/archiving for long-running history.
